## User Story

**Como** mantenedor do AIOX,
**quero** que os adaptadores CodeRabbit usem a interface suportada do CLI 0.9.x e validem autenticação, escopo e conclusão da revisão,
**para que** os gates nunca interpretem indisponibilidade, saída incompleta ou ambígua como revisão aprovada.

## Contexto e decisões

- A proposta `docs/quality/proposta-adequacao-gate-aiox-maven.md` revisão 10 recomenda a opção A: CLI autenticada revisando um range committed identificável por base/head SHA; CLI ausente, sem autenticação, com timeout, erro ou resultado sem escopo verificável permanece BLOCKED. Esta story implementa somente a adaptação dos consumidores CLI e seus testes.
- A proposta ainda **não é emenda constitucional aprovada nem política implementada**. Não alterar a Constitution, seus gates existentes, workflows/gates de Maven ou outras stories nesta story. Não elevar HIGH a bloqueador; preservar a política de severidade que estiver vigente no gate.
- Os consumidores atuais observados incluem `.aiox-core/core/quality-gates/layer2-pr-automation.js` e `.aiox-core/core/orchestration/workflow-executor.js`; ambos montam invocações com `--prompt-only -t ...` e tratam alguns estados de forma permissiva.
- A integração deve consumir saída estruturada do CLI, não inferir uma revisão limpa a partir de saída vazia/texto que o parser não reconheça. A especificação oficial atualmente documenta `coderabbit review --agent`, escopos `--committed`/`--uncommitted` e, a partir de 0.9.1, `--gate critical`; validar a disponibilidade exata desses argumentos e do contrato NDJSON com a versão 0.9.x efetivamente suportada durante a implementação. Não manter fallback silencioso para a sintaxe obsoleta.
- Para revisão committed, o SHA de base é passado como commit explícito suportado pelo CLI; o head é o HEAD completo capturado do checkout local. A execução valida o mesmo HEAD antes e depois do CLI. Se a versão suportada não conseguir provar o range completo ou a identidade base/head, o resultado é BLOCKED — não improvisar outro mecanismo nem declarar PASS.
- Os testes devem executar somente um fake CLI local, com fixtures sintéticas e sem rede, credenciais ou invocação do binário real. Nenhum resultado desta story deve ser descrito como uma revisão CodeRabbit real.
- Não há `accumulated-context.md` no checkout. O contexto cruzado utilizado é a proposta citada e o estado atual dos dois adaptadores.

## Acceptance Criteria

1. Os caminhos de review dos consumidores `Layer2PRAutomation` e `WorkflowExecutor` usam um adaptador comum, não contêm chamadas `--prompt-only -t ...`, e não têm fallback automático para essas opções. Para CLI 0.9.x, o adaptador usa a sintaxe `review --agent` e flags de escopo documentadas; só habilita `--gate critical` quando a versão suportada for 0.9.1 ou posterior. Versão ausente, fora do intervalo suportado ou incompatível bloqueia o check.
2. O construtor de comandos retorna invocações testáveis como executável + vetor de argumentos (sem `shell: true` para execução nativa). O modo nativo resolve o caminho configurado do CLI; o modo WSL converte o caminho do projeto para `/mnt/<drive>/...` e faz quoting seguro para diretórios/argumentos com espaços e caracteres especiais. Testes validam ambos os modos sem depender de Windows/WSL instalado.
3. Antes do review, o adaptador consulta `coderabbit auth status --agent` (ou a forma equivalente documentada para a versão mínima suportada) e só prossegue quando a resposta estruturada comprova autenticação válida. Estado falso, ausente, inválido ou ilegível resulta em BLOCKED; credenciais e saída sensível não aparecem em logs ou resultados.
4. Review committed exige base SHA e head SHA completos de 40 caracteres. O comando seleciona somente mudanças committed com `--committed --base-commit <BASE_SHA>` (ou forma equivalente comprovada para a versão mínima suportada); o head é capturado do checkout. O resultado registra ambos os SHAs e só pode ser aceito se o HEAD antes/depois da execução coincidir com o head esperado. Base/head ausente, inválido, divergente ou range não comprovável resulta em BLOCKED. Review uncommitted, quando mantido para o fluxo existente, não pode ser apresentado como review committed nem como evidência pre-push.
5. Resultado aprovado exige exit code de sucesso e stream NDJSON válido contendo contexto de revisão e exatamente um evento terminal `complete` com estado/outcome de conclusão íntegra. Eventos `error`, JSON inválido, linhas truncadas, falta/duplicação de conclusão, `outcome: failed`, review reutilizado, `unreviewedFileCount > 0`, saída sem evidência suficiente do escopo ou SHA divergente resultam em BLOCKED. Um exit code de finding bloqueador só é classificado como finding quando a saída estruturada comprova uma revisão completa; nunca como sucesso operacional vazio.
6. Timeout encerra o processo, retorna estado BLOCKED com motivo sanitizado e não pode gerar `pass: true`, `skipped: true` ou resultado equivalente. O mesmo comportamento se aplica a CLI ausente, erro de execução, falha de autenticação, exit code operacional não zero e saída vazia/malformada; somente finding de severidade coberta pela política vigente é reportado como finding, sem alterar os limiares da política.
7. Uma suíte de testes automatizados usa exclusivamente um executável fake em diretório temporário e um repositório Git temporário com conteúdo sintético; não executa o CLI real, não aponta o fake ao checkout Qas e não acessa rede/credenciais. Ela cobre no mínimo: construção nativa e WSL; revisão committed com base/head SHA; review completo sem findings; finding CRITICAL; autenticação inválida; exit code operacional de falha; timeout; NDJSON inválido; evento `error`; evento `complete` ausente/duplicado; review incompleto ou reutilizado; mudança de HEAD. Os testes confirmam que o fake foi invocado e que nenhum binário CodeRabbit real foi usado.
8. A mudança mantém a semântica de severidade existente: zero CRITICAL continua o critério vigente do gate onde aplicável; HIGH não se torna bloqueador por efeito desta story. Nenhuma definição/configuração de gate, Constitution, story existente ou código Maven é modificado; os dois consumidores existentes apenas passam a usar o adaptador testado. A entrega não afirma que CodeRabbit realizou uma revisão real; requer review formal de QA após implementação antes da transição da story para Done.

## Riscos e mitigação

- **Contrato da CLI pode diferir entre releases 0.9.x:** confirmar flags e schema de saída na documentação/help da versão mínima suportada; deixar versão/shape desconhecidos em BLOCKED e não criar fallback permissivo.
- **Saída parcial pode parecer limpa:** exigir contexto, eventos de saída e estado terminal coerentes, além do exit code; cobrir falhas após a emissão de findings.
- **Credenciais/trechos de código em erro:** sanitizar diagnósticos; não incluir conteúdo bruto do review, variáveis de autenticação ou mensagens que possam conter dados privados nos logs/resultados.
- **Deriva do checkout durante o review:** capturar e revalidar HEAD antes/depois; invalidar resultado em caso de mudança.
- **Teste acidental com CLI real:** injetar executável/runner fake e falhar o teste se qualquer processo diferente do fake ou Git sintético for iniciado; proibir chamadas de rede nos testes.
