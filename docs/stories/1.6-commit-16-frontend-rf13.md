# Story 1.6: Interface responsiva e integrada (RF-13)

**Epic:** Organização de Recursos — Entrega
**Story ID:** 1.6
**Sprint:** Commit 16 — Interface
**Priority:** High
**Status:** Review
**Type:** Feature / Delivery

## User Story

**Como** integrante da comunidade acadêmica,
**quero** consultar recursos e gerenciar minhas reservas em uma interface acessível e responsiva,
**para** usar o sistema sem depender diretamente do Swagger ou de chamadas manuais à API.

## Escopo e decisões

- Seguir RF-13 e o Commit 16 do roteiro: aplicação estática em `src/main/resources/static/`, HTML semântico, CSS e JavaScript puro, consumindo `/api/v1` no mesmo domínio.
- Os contratos de API, validações, paginação, status e permissões são os implementados no backend. A interface não simula respostas nem dados.
- A API de login retorna somente token, tipo e expiração; não há endpoint de identidade e o JWT não contém papel. A interface identifica capacidades consultando endpoints já existentes e protegidos, sem criar nova API.
- A SecurityConfig nega por padrão caminhos não mapeados. Somente `/`, `index.html`, `styles.css` e `app.js` serão liberados para servir a interface; endpoints da API continuam protegidos conforme as regras existentes.
- O backend não oferece fila de aprovações para responsáveis nem leitura de reservas de terceiros por responsáveis. O administrador poderá consultar a coleção que a API já permite; responsáveis poderão iniciar ações por UUID conhecido, sempre com validação final no backend.
- A aplicação usa `sessionStorage` para manter o token na sessão da aba; logout e 401 limpam a sessão. Valores da API são inseridos como texto, nunca como HTML.

## Acceptance Criteria

1. A página inicial apresenta login funcional em `/api/v1/auth/login`, consome `accessToken`, mantém sessão e oferece logout sem registrar token em logs.
2. A interface dispõe de dashboard com contagens obtidas da API, busca/listagem de recursos, disponibilidade por período, criação de reserva e consulta das reservas permitidas ao usuário.
3. Administradores autenticados têm gestão de recursos; responsáveis e administradores têm acesso às ações de aprovação/retirada/devolução que a API realmente permite, respeitando as limitações documentadas de leitura e fila.
4. Ações administrativas ou de responsável só aparecem depois de capacidades verificadas por endpoints protegidos existentes; a autorização do backend permanece definitiva.
5. Datas locais são convertidas para Instants ISO-8601 UTC nos payloads; paginação e enums refletem os DTOs do backend.
6. Erros HTTP (incluindo 400, 401, 403, 404, 409 e 500) apresentam mensagem compreensível, respeitam `fieldErrors` e não mostram detalhes internos.
7. A interface é utilizável por teclado e toque, tem estados de carregamento/sucesso/erro, e não apresenta overflow horizontal nas larguras de 320, 375, 390, 768, 1024 e 1440 pixels.
8. Recursos retornados pela API são exibidos com APIs seguras do DOM; nenhum conteúdo remoto é interpretado como HTML.
9. O CSS/JS estático é servido pelo Spring sem liberar rotas além dos arquivos explicitamente necessários; health, OpenAPI, Swagger e autorização das APIs permanecem funcionais.
10. README e esta story documentam como executar e acessar a interface, resultados reais de validação e limitações ambientais.

## Limitações conhecidas

- Sem endpoint de perfil, papéis não podem ser lidos diretamente; a interface usa a autorização efetiva dos endpoints de relatório e auditoria para determinar capacidades.
- Responsáveis não têm endpoint de consulta de fila ou de reservas de terceiros. A interface não inventa essa rota e oferece apenas ação por UUID conhecido.
- Não há endpoint para cadastro/listagem de usuários; o formulário de recursos não inventa uma lista de responsáveis.
